# Windows

Local Studio on Windows keeps the same shape as the other platforms: shared logic in `core/`, native chrome per platform. This page records the toolkit choice and what blocks a working build.

## Toolkit

The Windows app is C# on WinUI 3 (Windows App SDK), in `windows/`. It links the `kit` cdylib through UniFFI C# bindings generated by NordSecurity's `uniffi-bindgen-cs`.

- This matches `macos/`: a native UI language over the same UniFFI surface (`Studio`, its records and enums, and the `Waker` foreign trait). `uniffi-bindgen-cs` v0.12.0 targets uniffi 0.32, the line `kit` pins, and its tests cover foreign traits and callbacks.
- WinUI 3 gives Windows 11 chrome: Mica, the title bar, NavigationView, and the system theme and accent.
- It builds and packages (MSIX) on GitHub's `windows-latest` image with `cargo build` and `dotnet build`.
- The terminal grid comes from libghostty-vt as on the other platforms and is drawn with Win2D. libghostty-vt-sys 0.2.2 maps `x86_64-pc-windows-msvc` and builds with zig 0.15.2.

Rejected:
- GTK4 on Windows: no native chrome, and WebKitGTK has no Windows build.
- Rust bindings to WinUI 3: Microsoft archived `windows-app-rs`, and the community bindings cover only part of WinUI.
- Win32 wrapper crates such as native-windows-gui: no longer developed.

## What blocks it

`local-studio-core` does not compile for Windows today.

1. **Eukhe.** `eukhe-client` and `eukhe-types` are Unix-only. Eukhe's README says "No Windows", and its releases ship no Windows binary. The gaps:
   - `nix`, `libc` and `signal-hook` are unconditional dependencies of `eukhe-types`.
   - The only transport is `AF_UNIX` (`platform/transport.rs`).
   - `eukhe-client` compiles the `eukhe-bend` C core, which includes `sys/mman.h`, `poll.h` and `sys/select.h`.
   Under the rule that Eukhe changes land in the eukhe repo, a native Windows build needs these from Eukhe:
   - those dependencies gated to Unix;
   - a named-pipe transport;
   - `eukhe-bend` made optional in the client, or ported;
   - a Windows daemon in the release.
   A lighter fallback runs the daemon inside WSL2 and reaches it from Windows over loopback, but that still needs a client that compiles on Windows.
2. **Core's own Unix code** is small and gets fixed here:
   - Compile errors: `scratch.rs` (`MetadataExt::nlink`) and `workspace/providers.rs` (`DirBuilderExt`, `OpenOptionsExt` modes).
   - Wrong at run time:
     - process groups stopped through `/bin/kill`, where Windows needs Job Objects;
     - `/bin/sh`, `/bin/zsh` and `bash -c` fallbacks;
     - tool lookup that ignores `PATHEXT`;
     - data paths from `HOME` instead of `%LOCALAPPDATA%`;
     - XKB key codes for the terminal.
   `portable-pty` already has a ConPTY backend.

## Order

1. Core: put the Unix-only code behind `cfg`, with a Windows path for each item in point 2. Check with `cargo check --target x86_64-pc-windows-msvc`, where every remaining error must come from Eukhe's crates.
2. Eukhe: Windows support as listed in point 1, in the eukhe repo.
3. `windows/`: the WinUI 3 app, screen by screen against `macos/`. It starts with the window, sidebar, timeline and composer, and gets Windows CI in its own workflow.

Until step 2 lands, the Windows job in CI records the failure without blocking, and nothing Windows-specific ships.
